# 따릉이 수요 예측 및 재배치 지원 서비스

> 구현 계획서 · 2026-10-06 기준
>
> 현재는 서울시 실시간 재고 수집기, SQLite 저장소, FastAPI 조회 API, React 현황 대시보드가 연결되어 있다. 30분 수요 예측과 재배치 추천 모델은 아직 연결하지 않았다.

## 1. 프로젝트의 목적과 최종 결과물

따릉이를 이용할 때 원하는 대여소에 자전거가 없는 문제에서 출발했다. **향후 30분의 대여·반납량을 예측하고, 운영자가 어디에서 몇 대를 수거해 어디로 보충할지 판단하도록 돕는 서비스**를 만든다.

사용자는 따릉이 운영자다. 대시보드에서 다음 정보를 제공한다.

- 대여소별 현재 자전거 수와 30분 후 예상 재고
- 부족·과잉이 예상되는 대여소와 재배치 우선순위
- 권장 보충·수거 수량
- 가까운 과잉 대여소와 부족 대여소를 연결한 이동 추천
- 최근 재고 추이, 과거 평균, 예측 결과, 데이터 수집 상태

프로젝트의 중심은 **수집 → 정제·품질 검사 → 5분 집계 → 수요 예측 → 재배치 판단 → API·대시보드 → 평가**를 연결하는 것이다. 실제 차량 자동 배차나 현장 재배치 실행은 초기 범위에 포함하지 않는다.

### 핵심 계산

```text
30분 후 예상 재고 = 현재 재고 + 예상 반납량 - 예상 대여량
예: 현재 5대 + 반납 3대 - 대여 10대 = 예상 재고 -2대
```

`-2대`는 실제 자전거 수가 음수라는 뜻이 아니라, 단순 수급 계산상 2대의 부족 압력이 있다는 뜻이다. 원시 계산값은 판단에 보존하고 화면에서는 의미를 설명한다. 거치대 수를 넘는 예측도 과잉 압력으로 해석한다. 따릉이의 거치대 수를 실제 반납 가능량의 절대 상한으로 가정하지 말고 운영 규칙을 확인해야 한다.

| 데이터 | 서울시 API의 공식 대여소 재고를 5분 단위 수집 | 과거 대여·반납 이력 |
| 예측 | 시간대·규칙 기반 합성 수요 | 과거 평균과 학습 모델 비교 |

| 상세 | 정상 완료된 실제 수집 재고 추이 | 예측·과거 평균 비교 |

| 서버·DB | FastAPI + SQLite | PostgreSQL, Airflow, dbt |

현재 화면의 낮음·보통·많음은 현재 거치율 기반 상태이며 미래 예측이 아니다. 예측 영역은 모델 연결 전으로 표시한다.

### 현재 연결 결과

1. `GET /api/stations`가 마지막 전체 성공 수집의 대여소를 반환한다.
2. `GET /api/status`가 실행 ID·슬롯·행 수·지연 상태를 반환한다.
3. `GET /api/stations/{id}/history`가 정상 수집 재고 이력을 반환한다.
4. React가 현재 재고·거치율·실제 이력·가까운 대여소를 표시한다.
5. 표는 50개씩 페이지를 나눠 렌더링하며 상태·이름·재고 정렬을 지원한다.

Python 테스트 8개, TypeScript 프로덕션 빌드, 실제 SQLite 2,738개 대여소 API 응답과 Vite 프록시를 확인했다. 브라우저 시각 검수는 남아 있다.

## 3. 현재 대시보드 실행 방법

PowerShell 터미널 두 개를 연다. 첫 번째에서 FastAPI를 실행한다.

```powershell
Set-Location 'D:\졸업프로젝트'
.\.venv\Scripts\python.exe -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

두 번째 터미널에서 프런트엔드를 실행한다.

```powershell
Set-Location 'D:\졸업프로젝트'
npm.cmd run dev
```

수동 확인 순서:

1. 전체 대여소 수가 `python -m backend.collect --status`의 최근 정상 행 수와 같은지 확인한다.
2. 상태·검색 필터와 재고·거치율 정렬을 실행한다.
3. 지도 마커와 표 행을 선택해 같은 대여소 상세가 나오는지 확인한다.
4. 실제 재고 이력 시점 수와 수집 횟수를 비교한다.
5. 수집기를 한 번 더 실행하고 화면의 ‘최신 DB 조회’를 눌러 슬롯과 재고가 갱신되는지 확인한다.
6. 새로고침 로딩, 지연·누락 표시, 작은 화면에서 표 가로 스크롤을 확인한다.

## 4. 목표 구조와 기술 선택

```text
과거 대여·반납 이력 → 원본 저장 → 5분 집계 → 특징·정답 생성 → 모델 학습
대여소 마스터 ─────→ ID 매핑 ───────────────────────────────┐
실시간 재고 API ───→ 5분 수집 → 원본 저장 → 품질 검사 → 현재 재고 │
                                                           ↓
                    현재 사용 가능한 특징 + 저장된 모델
                                                           ↓
                      대여·반납 예측 → 예상 재고 → 재배치 추천
                                                           ↓
                         결과 저장 → FastAPI → React 대시보드
```

5분은 **우리 시스템의 목표 수집·계산 주기**다. 제공기관의 갱신 주기나 과거 이력 공개 주기가 5분이라는 뜻은 아니다.

| 구성 | 초기 선택안 | 목적 |
|---|---|---|
| 웹 화면 | 기존 React + TypeScript | 현재 화면 확장 |
| 수집·집계·학습 | Python + pandas | CSV 정제부터 모델 학습까지 연결 |
| 기준 모델 | 같은 요일·시간대 과거 평균 | 빠르고 설명 가능한 비교 기준 |
| 첫 학습 후보 | HistGradientBoostingRegressor | 시간·지역·과거 통계 기반 회귀 |
| API | FastAPI | 저장된 예측과 이동 추천 제공 |
| 원본·집계 저장 | JSON/CSV + Parquet | 원본 보존과 재처리 |
| 운영 결과 저장 | 우선 SQLite | 단일 PC에서 구현, 이후 필요 시 PostgreSQL |
| 주기 실행 | Python 단일 작업 루프 또는 Windows 작업 스케줄러 | 5분 작업 실행과 실패 기록 |

이 표는 향후 구현 제안이다. Kafka, Spark, Airflow, 딥러닝, 클라우드 배포는 초기 필수 항목으로 두지 않는다. 먼저 지역을 좁혀 전체 흐름을 완성한 뒤 처리량과 운영 필요를 측정하여 확장한다.

## 5. 데이터 확보와 설계

### 5.1 실제로 먼저 할 일

1. [서울 열린데이터광장 공공자전거 자료 목록](https://data.seoul.go.kr/dataList/5/literacyView.do)에서 실시간 대여정보, 대여이력, 마스터, 시간대별 운영현황을 찾는다.
2. 제공 기간·필드·샘플·갱신 주기·호출 제한·이용 조건을 기록한다. API 인증이 필요하면 키를 발급받는다.
3. 대여이력 파일 하나를 받아 대여·반납 시각과 대여소 식별자를 확인한다. 시간별 합계만 있으면 이를 임의로 나누어 5분 정답을 만들지 않는다.
4. 실시간 응답과 마스터를 대조하여 공식 ID와 대여소 번호의 연결표를 만든다. 이름만으로 연결하지 않는다.
5. 초기 실험은 서로 가까운 20~50개 대여소를 선택한다. 서울 전역의 더미 화면과 실제 인접 지역 실험을 구분한다.
6. 가능하면 과거 8~12주 이력을 확보하고, 현재부터 실시간 재고를 누적한다. 공개 지연 때문에 학습 기간과 실시간 시연 기간이 다를 수 있다.

실시간 재고 API 접근과 수집은 확인했다. 과거 대여·반납 이력의 기간·해상도·필드는 별도로 확보하고 검증해야 한다.

### 5.2 데이터별 역할

| 데이터 | 주요 정보 | 역할과 주의점 |
|---|---|---|
| 대여소 마스터 | ID, 번호, 명칭, 좌표, 거치대 수 | 지도·거리·식별자 통합. 개명·이전·폐쇄 관리 |
| 실시간 재고 | 대여 가능 수량, 원본 관측 시각 | 현재 재고와 검증용 스냅샷. 재고 차이만으로 대여·반납을 각각 복원할 수 없음 |
| 대여·반납 이력 | 출발·도착 대여소와 각각의 시각 | 5분 집계와 학습 정답 |
| 시간별 운영현황 | 시간별 재고·거치율 | 장기 패턴 보완. 5분 관측값처럼 취급하지 않음 |
| 날씨, 선택 사항 | 기온·강수·관측 시각 | 추가 특징. 예측 시점 이후 관측 날씨를 입력하지 않음 |

샘플로 UTF-8/CP949 등 인코딩을 확인한다. 원본 파일은 보존하고 정제 파일을 별도로 만든다. 이용자 관련 열이 있어도 이 서비스에는 필요하지 않으므로 정제·서빙에서 제외한다.

### 5.3 한 행과 시간의 정의

학습 테이블 한 행은 **대여소 1곳 × 예측 기준 시각 t(5분 경계)**다. 저장 시간 기준을 통일하고 화면은 `Asia/Seoul`로 표시한다.

```text
t = 08:00
마지막 완료된 입력 구간: [07:55, 08:00)
정답 구간: [08:00, 08:30)
대여 정답: 위 30분 동안 해당 대여소에서 출발한 건수
반납 정답: 위 30분 동안 해당 대여소에 도착한 건수
```

반납은 대여 시각이 아닌 실제 반납 시각으로 집계한다. 구간은 시작 포함·끝 제외로 통일한다. 누락은 null과 품질 플래그로 남기고, 관측이 완전한데 사건이 없을 때만 0건으로 채운다.

### 5.4 저장 테이블 설계안

| 테이블 | 키 | 주요 필드 |
|---|---|---|
| stations | station_id | 번호, 이름, 지역, 좌표, 거치대 수, 운영 여부 |
| snapshots | station_id + snapshot_slot | current_bikes, source_observed_at, fetched_at, quality |
| flows_5m | station_id + interval_start | rentals, returns, coverage, available_at |
| features_5m | station_id + as_of + feature_version | 입력 특징, target_rentals_30m, target_returns_30m |
| predictions | station_id + as_of + model_version | 예측 대여·반납, 원시 예상 재고, 상태, 품질 |
| relocation_plans | plan_id + step | 출발·도착 ID, 수량, 거리, 누적 이동 후 재고 |
| job_runs | run_id | 작업명, 시작·종료, 성공 여부, 입력·출력 건수, 오류 |

`fetched_at`은 우리가 받은 시각이다. 원본 관측 시각이 없으면 수집 성공만으로 최신 데이터라고 단정하지 않는다. 같은 슬롯을 재수집할 때 중복을 방지하고, 원본 응답·요청 범위·오류 상태를 기록한다.

## 6. 예측 모델 계획

### 6.1 기준 모델: 같은 요일·시간대 평균

`seasonal-mean-v1`은 학습 기간의 동일 대여소·요일·5분 시각별 향후 30분 대여량과 반납량 평균을 사용한다. 표본이 부족하면 대여소별 평일/주말·시간대 평균, 지역 평균 순서로 대체한다. 평균에는 예측 시점 이후 데이터가 포함되지 않아야 한다.

이 모델로 수집부터 화면까지 먼저 연결한다. 학습 모델이 개선되지 않으면 기준 모델을 유지할 수 있다.

### 6.2 첫 학습 후보: 히스토그램 기반 그래디언트 부스팅

`HistGradientBoostingRegressor`로 **대여량 모델과 반납량 모델을 각각** 만든다. 대상 대여소를 묶어 학습하고 ID는 범주형으로 처리한다. 제곱오차와 `loss="poisson"`을 비교한다. Poisson 손실에는 비음수 정답과 양수 정답 합계가 필요하므로 전체 정답이 0이면 평균 모델로 대체한다. 지원 조건은 [공식 문서](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.HistGradientBoostingRegressor.html)를 따른다.

초기 설정 예시는 `max_iter=200`, `learning_rate=0.05`, `max_leaf_nodes=15`, `early_stopping=False`, `random_state=42`다. 최적값이 아니라 비교 실험의 시작점이다. 내부 무작위 검증 대신 외부 시간순 검증으로 설정을 선택한다.

| 입력 특징 | 사용 계획 | 조건 |
|---|---|---|
| 요일, 시간, 5분 슬롯, 주말 여부 | 초기 사용 | 예측 시점에 알 수 있음 |
| 대여소 범주, 좌표, 거치대 수 | 초기 사용 | 해당 시점 마스터 정보 |
| 과거 동일 요일·시간대 평균 | 초기 사용 | 학습 구간 또는 시점 이전 데이터만 사용 |
| 최근 5·15·30·60분 대여·반납 | 조건부 | 실제 운영 시점에 이력을 얻을 수 있을 때 |
| 현재 재고와 최근 변화 | 후속 실험 | 학습·운영 모두 동일 해상도의 관측이 있을 때 |
| 기온·강수 | 후속 실험 | 당시 이용 가능했던 관측·예보만 사용 |

**과거 대여이력이 며칠 뒤 공개된다면 최근 30분 대여량을 실시간 입력으로 사용할 수 없다.** 초기 운영 모델은 달력·마스터·과거 계절 통계처럼 실제 가용한 특징으로 만든다. 최근 흐름을 사용하는 오프라인 모델은 별도 실험으로 구분한다. 과거 재고가 시간별뿐이면 임의의 5분 재고를 실측값처럼 학습시키지 않는다.

LSTM·Transformer는 연속 시계열과 기준 실험 결과가 확보된 뒤 확장 후보로 검토한다. 모델 이름보다 기준 모델 대비 개선과 재현 가능한 검증을 우선한다.

### 6.3 30분 합계와 중간 예측 곡선

첫 모델은 30분 합계를 직접 예측한다. 이 경우 중간 5·10·15분 값은 실제 모델 출력이 아니다. 선형 보간으로 표시하면 보간값이라고 표시한다. 이후 미래의 각 5분 구간을 따로 예측하면 누적 대여·반납량으로 재고 곡선을 만들 수 있다.

### 6.4 학습·검증 절차

1. 12주 확보 시 앞 8주 학습, 다음 2주 검증, 마지막 2주 테스트로 분할한다. 기간 부족 시 실제 기간을 기록하고 규모를 줄인다.
2. 모든 대여소에 동일한 시간 경계를 적용한다. 행을 무작위로 섞지 않는다.
3. 30분 정답 구간이 다음 분할로 넘어가지 않도록 이전 분할 끝의 30분 기준 시각을 제외한다.
4. 평균 통계·범주 변환·결측 대체 규칙은 학습 데이터로만 만든다. 원본의 공개 지연과 이용 가능 시각을 반영한다.
5. 검증으로 모델과 설정을 선택하고, 마지막 테스트는 최종 비교에만 사용한다.
6. 모델 파일, 특징 목록, 학습 기간, 설정, 데이터 버전, 평가 결과를 함께 저장한다.

평가 지표:

- 대여·반납 각각 MAE와 RMSE. 0건이 많으므로 MAPE를 주 지표로 삼지 않는다.
- 전체 평균뿐 아니라 대여소별·출근·낮·퇴근별 오차를 비교한다.
- 30분 후 실제 재고를 확보한 기간에는 재고 MAE와 부족 탐지 precision/recall을 추가한다.
- 실제 재고 변화에는 운영자 이동·정비·원본 오차도 포함될 수 있으므로 수요 예측 오차와 재고 보존식 잔차를 분리한다.
- 자전거가 없어 발생하지 못한 대여는 기록에 없다. 관측 대여량 예측을 잠재 수요 전체의 예측으로 주장하지 않는다.

## 7. 재배치 로직과 검증

### 7.1 상태와 권장 수량

초기에는 현재 코드의 비율을 설정값으로 분리해 사용한다. 실제 운영 기준으로 확정된 값은 아니다.

```text
L = ceil(거치대 수 × 0.2)       # 부족 기준
H = floor(거치대 수 × 0.8)      # 과잉 기준
T = round(거치대 수 × 0.5)      # 목표 재고
E = 현재 재고 + 예상 반납 - 예상 대여

E <= L : 부족 / E >= H : 과잉 / 나머지 : 정상
보충 필요량 = ceil(max(0, T - E))   # 부족 대여소
수거 여유량 = floor(max(0, E - T))  # 과잉 대여소
```

예측은 소수로 보존하고 실제 이동량만 정수로 만든다. 작은 거치대 수에서 L < H인지 검사한다. 목표 비율 변경에 따른 이동 수량도 비교한다.

### 7.2 초기 추천 알고리즘

1. 정상 수집 대여소 중 부족 대여소를 보충 필요량 내림차순으로 정렬한다. 동률은 예상 재고·ID 순으로 고정한다.
2. 설정 반경 안의 과잉 대여소를 직선거리순으로 찾는다. 반경은 예를 들어 3km부터 실험한다.
3. `min(남은 보충 필요량, 출발지 남은 수거 여유량, 출발지 현재 가용량, 1회 이동 한도)`만큼 배정한다.
4. 매번 출발지 가용량과 도착지 필요량을 차감한다. 미충족분이 있으면 다음 출발지를 검토한다.
5. 양쪽의 이동 후 예상 재고를 누적 반영한다. 수량이 0이면 추천하지 않는다.
6. 공급지가 없으면 미충족 수량과 사유를 표시한다.

지연·누락 대여소는 화면에 남기되 실행 후보에서 제외한다. 같은 예측 시점·모델 버전의 결과끼리 연결하며, 이동 전후 전체 수량 합계가 보존되는지 확인한다.

초기 이동 한도 8대는 시연용 설정이지 확인된 실제 차량 적재량이 아니다. 여러 추천의 합계도 단일 차량 운행 계획이 아니다. 직선거리와 임의 속도로 얻은 시간은 실제 도로 거리·소요시간이 아니다. 차량별 운행 순서와 도착 시각을 반영하는 최적화는 후속 범위로 둔다.

### 7.3 운영 효과 평가

같은 초기 재고와 같은 관측 대여·반납 사건으로 무재배치, 현재 재고 기반, 예측 기반 정책을 시뮬레이션한다. 이동 예산·거리 한도·도착 지연을 동일하게 두고 부족 지속 시간, 시뮬레이션상 미충족 대여, 이동 수량·거리를 비교한다.

이는 실제 재배치 효과의 현장 검증이 아니다. 관측되지 않은 잠재 수요와 정책 변화에 따른 이용자 행동은 반영하지 못한다는 한계를 보고한다.

## 8. API와 화면 연결 설계

API 키는 서버 환경변수 `SEOUL_API_KEY` 등에 저장한다. 프런트엔드의 `VITE_API_BASE_URL`에는 우리 서버 주소만 둔다.

| API 설계안 | 역할 |
|---|---|
| GET /health | 서버·최근 작업 상태 |
| GET /stations?status=&district=&q=&sort= | 같은 기준 시각의 대여소·예측 목록 |
| GET /stations/{id}/history | 관측·예측·과거 평균 곡선 |
| GET /relocations?asOf= | 해당 예측 묶음의 이동 추천 |
| GET /runs/latest | 마지막 수집·추론·오류 상태 |

정기 수집은 서버가 실행한다. 화면 새로고침은 이미 계산된 최신 결과를 조회한다. 클릭마다 외부 API 수집을 새로 실행하지 않는다. 과거 시간대 비교는 저장된 스냅샷 재생 모드로 구분한다.

응답 예시(설계용 더미):

```json
{
  "stationId": "ST-101",
  "asOf": "2026-10-06T08:00:00+09:00",
  "horizonMinutes": 30,
  "currentBikes": 5,
  "expectedRentals30m": 10,
  "expectedReturns30m": 3,
  "expectedBikesRaw30m": -2,
  "recommendedReplenishment": 12,
  "status": "shortage",
  "modelVersion": "seasonal-mean-v1",
  "dataQuality": "normal",
  "sourceObservedAt": "2026-10-06T08:00:00+09:00",
  "fetchedAt": "2026-10-06T08:00:10+09:00"
}
```

보충량 12대는 거치대 20개·목표 재고 10대라는 가정이다. 최초 요구 예시의 보충량 7대는 목표 5대를 뜻하므로 목표 정책을 명확히 정해야 한다. API 이름과 현재 화면의 `current`, `rentals`, `returns` 차이는 변환 함수 한 곳에서 처리한다.

로딩·빈 결과·서버 오류·수집 지연은 서로 다른 상태로 표현한다. 마지막 성공 결과를 유지할 때 기준 시각을 표시한다. 장애를 부족 대여소 0개로 보여주면 안 된다.

## 9. 직접 따라갈 단계별 구현 순서

아래는 상대 일정이다. 데이터 확보 상황에 따라 조정한다.

### 단계 1: 다음 면담 전 프로토타입과 모델 제안

1. 3장의 실행 명령으로 현재 화면을 확인한다.
2. `src/App.tsx`의 더미 생성·상태 분류·재배치 함수를 `src/domain/`으로 분리한다.
3. 2장의 시각 불일치, 필터, 누적 재고, 후보 선택 문제를 수정한다.
4. 새로고침마다 더미 시각을 5분씩 진행시키고 합성값을 명확히 표시한다.
5. 공식 원본 샘플로 필드·공개 주기·식별자 매핑을 기록한다.
6. 과거 평균을 기준 모델, 부스팅을 첫 학습 후보로 제안하고 시간순 평가 방법을 설명한다.

완료 기준: 동작 화면 시연, 필요한 입력·출력 설명, 모델 후보와 평가 방식 설명이 가능하다. 학습 모델이 완료된 것으로 보고하지 않는다.

### 단계 2: 데이터 수집과 집계

1. `backend/`, `data/raw/`, `data/processed/`, `models/`, `reports/`를 만든다.
2. Python이 설치된 환경에서 가상환경과 백엔드용 패키지를 준비한다.

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install pandas pyarrow httpx scikit-learn fastapi uvicorn
```

3. `.gitignore`에 `.env`, `.venv/`, `data/`, `models/`, `node_modules/` 등을 추가하고 검증된 패키지 버전을 requirements 파일에 고정한다.
4. `backend/collect.py`를 작성한다. 응답 샘플 파싱 → 호출 범위 분할 → 원본 저장 → 타임아웃·재시도 → 작업 로그 순서로 구현한다. 부분 실패를 전체 성공으로 기록하지 않는다.
5. `backend/aggregate.py`에서 대여·반납을 각각 사건 시각으로 5분 집계하고 마스터와 연결한다.
6. 원본 건수와 집계 합계, 경계 사건 중복, 같은 파일 재실행 시 중복 발생 여부를 검사한다.
7. 5분 경계 실행과 동시 중복 실행 방지를 구현한다. 수집 실패는 누락으로 기록한다.

완료 기준: 선택 지역의 원본·집계 파일, 수집 성공률·결측률, 재실행 가능한 집계 과정이 있다.

### 단계 3: 모델 학습과 비교

1. `backend/features.py`에서 시점별 특징과 미래 30분 정답을 만든다.
2. `backend/train.py`에서 시간순 분할과 과거 평균 모델을 구현한다.
3. 동일 분할로 대여·반납 회귀 모델을 훈련한다.
4. `backend/evaluate.py`에서 MAE/RMSE와 시간대별 결과를 계산한다.
5. `reports/model_comparison.csv`에 모델·기간·특징·지표를 기록한다. 개선이 없으면 평균 모델을 유지하고 원인을 분석한다.
6. 전처리 정보·모델 파일·학습 기간·버전을 함께 저장한다.

완료 기준: 숫자로 비교 가능한 기준 모델과 후보 모델 결과, 누출 없는 분할, 재현 가능한 학습 절차가 있다.

### 단계 4: API 연결과 주기 갱신

1. `backend/predict.py`가 새 시점의 특징을 읽어 결과를 저장하게 한다.
2. `backend/rebalance.py`에 수량 제약과 누적 차감을 구현한다.
3. `backend/main.py`에 8장의 API를 작성하여 저장된 결과를 제공한다.
4. `src/api/`에 서버 호출·응답 변환 함수를 만들고 더미/API 모드를 분리한다.
5. 마지막 성공 결과와 오류를 함께 처리하고, 개발 CORS는 프런트엔드 주소로 제한한다.

현재 FastAPI 조회 API와 프런트 연결은 구현되어 있다. 예측·재배치 엔드포인트는 이후 추가한다.

```powershell
# 백엔드 구현 후 실행
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload --port 8000

# 별도 터미널에서 기존 프런트엔드 실행
npm.cmd run dev
```

완료 기준: 서버에 저장된 결과가 화면에 표시되고 기준 시각·모델 버전·품질을 확인할 수 있다.

### 단계 5: 재배치 평가와 발표

1. 동일 조건으로 무재배치·현재 재고 기반·예측 기반 정책을 비교한다.
2. 예측 오차와 재배치 효과를 별도 표로 제시한다.
3. 지연·누락·서버 장애·빈 검색·공급지 없음 상황을 시연한다.
4. 데이터 흐름, 모델 비교, 한계를 정리한다.
5. 실행 안내와 작은 재현용 샘플을 제공한다. 원본 재배포는 제공기관 조건을 확인한다.
